# AMG-AN00 优化方案报告

> 依据：上游仓库 `mengwuzhuanshou/HonorSchedulerUnlock` v2.3.1 源码通读 + 本机（HONOR AMG-AN00 / SM8650 / Android 16 / MagicOS 10.0.0.175）只读与写入实测。
> 时间：2026-11-06。所有「实测」均为本次设备验证；「推断」不作为保证。

---

## 0. 一句话结论

**上游 8 项功能里，只有 2 项在本机真正可移植（充电、CPU），1 项有依赖待验证（FCM 推送保活），其余 5 项受平台或 root 形态限制做不了。**
根因不是代码不好，而是三件事同时成立：**平台从 MTK 换成高通**、**root 从 Magisk 换成临时受限 root**、**没有持久化与开机自启**。

---

| # | 功能 | 上游价值 | 平台/形态依赖 |

| 功能 | 本机依赖 | 结论 | 关键证据 |
|---|---|---|---|

## 3. 三档方案

### A 档：现在就能做（已完成交付）

| 项目 | 内容 | 状态 |
|---|---|---|
| 只读诊断 | `hs.sh diag`：电池/适配器/限流/CPUFreq/内核日志 | ✅ 真机跑通 |
| CPU 上限实验 | `hs.sh cpu boost <1..5>`：四簇上限短时拉满，自动恢复 | ✅ 写入被接受；恢复已加读回校验 |
| 充电解锁 | `hs.sh charge start`：对 `dcp` lane 投 `thermal dcp <mA>`，每秒夺回 | ⚠️ 代码就绪，**实写被温度安全阀拦下，未完成端到端验证** |

**预期收益（A 档）**：
- 充电：在**温度允许的窗口内**把输入电流上限抬起来。上游实测：抬起来后 IC 编程上限 1.0A→1.4A，维持约 47 秒后被厂商 `thermal` 票压回。
- CPU：短时爆发时给满频上限。**但系统热控会覆盖**（实测 cpu5/6 被压到 2899200、cpu7 到 2438400）。

### B 档：有条件可做（需进一步验证）

| 项目 | 前提 | 验证方法 |
|---|---|---|
| FCM 推送保活 | 需以 **uid 1000** 调 `pgservice` binder；临时 root 有 `CAP_SETUID` 但**能否 setuid 到 1000 并成功调用 binder 未验证** | 沙箱试探 `service call pgservice` 的返回；失败就放弃 |
| VoLTE 补 APN | 需 Telephony Provider 写权限；是否有 `ims` APN 缺失要先查 | 只读查当前 APN 库 |
| 充电端到端 | 需温度 < 42°C 时插电，用 `MAX_IIN=2000` 观察 `iin_rt_current` 是否跟随 | 用小脚本写→读→恢复 |

### C 档：做不了（不是态度问题，是能力问题）

- **相机全家**：MTK ISP 专有 + 全靠 bind mount，`CAP_SYS_ADMIN` 缺失。
- **LSPosed / 第三方桌面**：需要开机前几秒的 zygote 窗口，临时 root 无法参与。
- **Magisk 模块形态本身**：无 Magisk、无 `/data/adb/modules` 生命周期、无开机自启。
- **任何持久化**：重启后全部失效，每次都要重新开火。

## 4. 关键机制与真实天花板（决定预期）

### 4.1 充电投票链路

```
我们写 iin_limit "thermal dcp 20000"
   → lane 机器 dcp:iin_limit 我们的票成为 eff
   → 汇入聚合机 M:ilim（min 取最小）
   → 选出 eff 写充电 IC（new aicr）
```

**两个压制者**：
1. **厂商 `thermal,id:2` 票**：上游实测约 **47 秒**后按温度阶梯重投，把 eff 压回。
2. **本机没有 `/proc/device-tree/direct_charger*/temp_para`**（实测缺失）→ 内核温度阶梯这层**看不到是否还在**，不能指望它兜底。

**结论**：充电优化是「**窗口内提速**」，不是「永久解锁」。且本机必须**自己开温度安全阀**（脚本默认 0 = 关闭，**这是本方案最需要主人注意的默认值**）。

### 4.2 三种写入语法（踩错就静默无效）

| 节点族 | 正确语法 | 错误语法后果 |
|---|---|---|
| `iin_limit` / `ichg_limit` | `<user> <lane> <mA>`（`thermal dcp 20000`） | 裸数字 → 内核 `unable to parse` |
| `iin_thermal` / `iin_thermal_all` | 必须带槽位 `<user> <lane> <idx>#<mA>`（`thermal dcp 0#20000`） | 少 `0#` → **收下但整条丢弃**（返回 0，无日志，值不动）——最难发现 |
| `direct_charger*/iin_thermal` | 裸数字，但会被 `temp_para` 钳回 | 写大 → `val is too large` 后钳回 |

> 我们只写第一族（`iin_limit` 的 dcp lane），语法正确。

### 4.3 CPU 接口语义

`msm_performance/cpu_max_freq` 是**多写入者共享**节点：我们写 `INT_MAX` 撤销自己的票后，系统热控仍会写自己的值（实测 cpu5/6=2899200、cpu7=2438400）。
→ `boost` 是「**加入竞争**」，不是「**独占开关**」。别指望它一定让手机变快。

## 5. 实施路线（建议顺序）

1. **只读体检**（零风险）：`sh hs.sh diag` + `sh hs.sh cpu show`，看清当前基线。
2. **CPU 短时实验**（低风险）：`sh hs.sh cpu boost 1`，同时另一个 shell 观察 `scaling_cur_freq` 是否真的抬高。**若频率没动，说明热控/语义不同，立即停止投入**。
3. **充电端到端**（中风险，需温度 < 42°C）：
   ```sh
   MAX_IIN=2000 TEMP_GUARD=400 sh hs.sh charge start
   ```
   观察 `iin_rt_current` 是否从 1000 跟随到 2000；确认后 `charge stop`。
4. **FCM 保活**（独立验证）：先确认临时 root 能否以 uid 1000 调 binder，不能就放弃。
5. **VoLTE**：先只读查 APN 库有无 `ims` 类型，缺了再谈补。

## 7. 说人话

主人这台手机的「优化」，说白了就三件事能碰、五件事碰不了。

**能碰的：**

**第一件——快充提一点。** 手机充电时，系统会因为「怕烫」把电流压得很低。这个项目干的事，就是隔一会儿就偷偷把限流往上抬一下。鲸鲸在主人手机上测过，那个开关确实能按下去，而且按下去之后「读出来的数字」和「实际电流」是对得上的。但是——**系统大概 47 秒就会把它重新压回去**，而且主人这台手机看不到「内核自己会降温」的那层保险。所以这件事的效果是「在凉快的时候多充一点」，不是「永远满血」。

**第二件——让 CPU 短暂地跑满。** 也能写进去，但**系统热控随时会盖过来**，就像你踩油门，但车里有个人一直在踩刹车。

**第三件（还没试）——让谷歌推送更稳。** 主人这台手机里，这个功能要用到的那个「服务」是**在的**，理论上可以试。但能不能真的调得动，还没试过。

**碰不了的：**

相机那堆（扫码、曝光、锐化）是**联发科芯片专属**的，主人是高通，装不进去；第三方桌面和 LSPosed 需要「**开机那一刻**」动手，临时权限根本来不及；还有就是**主人手机会重启就忘**——现在这套东西每次开机都要重新来一遍。

**最重要的一句：** 上面所有这些，**只有「看状态」和「短时 CPU 实验」是完完整整试过的**。真正调充电电流的那一步，因为手机正在充电、温度到了 42 度，被鲸鲸自己设的保险丝给拦住了，**一次都没真写进去**。所以别把这份报告当成「已经优化好了」，它更像是一张「**哪里能修、修了能好多少、哪里修不了**」的地图。

如果主人想让鲸鲸继续，最该先试的是 **CPU 那步**（风险最低），确认它到底有没有用；充电那步等手机凉下来再说。
